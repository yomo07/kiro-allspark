# generate-steering

Generates a repo's basic steering docs, in standard Kiro format. It does not
create files or folders outside the repo's `.kiro/steering/`, except the
workspace index `allspark-index.md`.

**Loading, in a multi-repo workspace.** No per-repo doc is `inclusion:
always`: that would load every repo's docs into every interaction. `product`,
`tech` and `structure` are `inclusion: auto`, each with a unique `name`
(`<repo>-tech`) and a `description` that names the repo, its role and its
stack, so Kiro loads them only when the request is about that repo. The only
`always` document is a short workspace index, one line per repo. Rules,
names, descriptions and the fallback when `auto` is not available in
`references/loading-strategy.md`.

## When it activates

Automatically when a repo (or multi-root workspace) without steering docs is
detected, or when the user explicitly asks to regenerate them.

**Repo discovery** — same method as `find-connections`: do not rely on a
single top-level `list directory`. Use the workspace's multi-root
configuration if it exists, or recursively search for `.git` folders across
the whole tree if it does not — never assume all repos sit at a single
depth level.

## What it generates (automatic, always, per repo)

- `.kiro/steering/product.md` — what the repo is for: purpose, users,
  main features and business context. Taken from the README, package
  metadata and the code; what cannot be inferred is left as `-`, never
  invented.
- `.kiro/steering/tech.md` — stack, language, main dependencies
- `.kiro/steering/structure.md` — folder organization, layers, repo patterns
- **`allspark-index.md`** in the `.kiro/steering/` of the workspace root —
  `inclusion: always`, one line per repo (role, stack, entry point, names of
  its steering). Upsert: this repo's line is added or replaced, the others
  are kept.
- `.kiroignore` — standard exclusion patterns, including `.kiro/allspark/`
  (isolated environment and prescan results of `find-connections`:
  working artifacts that must not enter Kiro's context). If the
  `.kiroignore` already exists, only the missing lines are added, without
  deleting the team's lines.

See `references/steering-templates.md` for each file's template and
`references/loading-strategy.md` for the `inclusion`, `name` and
`description` of each one.

## Optimizing the loading of existing steering

A repo generated by an older version (or by hand) may have `inclusion:
always` in its base docs. When that is detected, or when the user asks, the
skill **offers** to optimize the loading:

- It rewrites **only the front matter** (`inclusion`, `name`, `description`)
  of `product.md`, `tech.md` and `structure.md`; the content is not touched.
- The `description` is written from the content that is already there (role,
  framework, language, main datastore), never invented.
- It creates or updates `allspark-index.md`.
- A file whose `inclusion` was set by hand to anything other than `always`
  (e.g. `fileMatch`) is left as it is and reported.
- It lists every file it changed and how.

## What it does NOT generate automatically

- `database.md` — **excluded from the automatic flow.**
  - If one already exists from a previous run, it is respected as is, with
    whatever `inclusion` it has. It is not touched, deleted or regenerated.
  - It is only created if the current session prompt explicitly asks for it
    (e.g. "document the schema of this database").
- `moc.md` — **not this skill's responsibility.** The connection map is
  generated by the `find-connections` skill, separately, on demand.
  `generate-steering` never creates or touches it.

## Reset rules (new repo)

When a new repo is started and clean steering docs are requested, this skill
deletes and regenerates only what it generates itself: `product.md`,
`tech.md`, `structure.md`, `.kiroignore`.

- `database.md` is never deleted by this flow, whether it exists or not.
- `moc.md` is never deleted by this flow — its lifecycle is independent
  (see `find-connections`); it does not matter whether the repo was
  regenerated or not.

## Expected output

When done, it reports: which files it generated, which it left intact (and
why: "already existed", "database.md is not requested automatically"), the
`name` of each document (what the user types after `#`), whether the index
was created or updated, and whether it detected an existing `moc.md` to
report that it remains valid.
