# manage-allspark

`find-connections` generates the connections MOC and the graph notes from
each repo's code. `manage-allspark` does not generate content — it
manages the relationship between what you generated locally and the shared
vault, which is a single source across teams (see
`references/notification.md` for the repo master registry,
`references/vault-notes.md` of `find-connections` for the note
format, and "Multi-team merge between vaults" in `references/moc-schema.md`
for the underlying merge rules).

It is invoked manually; it does not run as part of the other skills.

## When to use it

After running `find-connections` and having new or updated local files that
are not yet reflected in the shared vault, or when you want to bring in
what other teams already uploaded before continuing to map repos.

## Team notification (see `references/notification.md`)

There is no access control or admin that approves — it is an open power;
anyone on the team can run any operation. The only thing the power does,
before adding a new repo to the master registry, is **suggest** informing
the team — it never blocks the action if the user does not want to
notify.

## Operations

### `feed` — upload local work to the shared vault

1. Identifies which local files (each repo's MOC and point notes in
   `allspark/graphs/`) are new or modified since the last
   sync with the shared vault.
2. For each file, applies upsert against the shared vault — never a
   full replacement:
   - New file (does not exist in the shared vault) → added directly.
   - Existing file with no parallel changes on the other side → updated
     without friction.
   - Existing file that the shared vault also modified since the
     last sync → **real conflict**; it is not resolved automatically, it goes
     to the `resolve` queue.
3. Special case — **merging a virtual point into a real point**: if any of
   the files to upload triggers a merge (see
   `references/vault-notes.md` of `find-connections`), treat the
   operation as atomic: the merged point and every repo note that pointed
   to it travel together in the same upload. If any of those "pointing"
   notes was touched in parallel by another team, the whole merge goes
   to conflict — it is not uploaded halfway.
4. Nothing is ever deleted on the shared vault side during `feed`.
   What is no longer detected locally is marked
   `status: not-detected-last-run`; it does not disappear.
5. **Derivatives — not merged:** `allspark/export/allspark.md` and
   `allspark/export/allspark.html` are compiled from the notes. If
   they differ on the shared side, they are not a conflict: `allspark.md` is
   regenerated after the notes merge, and `allspark.html` is marked outdated
   (it is only regenerated by going through the `generate-visual` gate).
6. **`.kiro/allspark/`** (prescan environment and JSON) is local to each
   workspace: it is never uploaded to the shared vault or merged.
7. **`allspark/graphs/.obsidian/graph.json`** is uploaded only with the
   power's three color entries (see `vault-notes.md`); each person's groups
   and personal settings do not travel.

### `sync` — bring in what is new from the shared vault

1. Brings into the local workspace the files that the shared vault has and
   the local one does not, or that changed on the shared side since the last
   sync.
2. Same upsert criterion as `feed`, in the reverse direction: it does not
   overwrite local work not yet uploaded.
3. Recommended before running `find-connections`, so as not to re-map a
   repo that another team already mapped.
4. If it brought changes that affect the cube (points or vectors), it
   regenerates `allspark.md` and **asks** whether to generate or update the
   HTML visualization (yes/no gate of `generate-visual`); without a "yes" no
   HTML is written.

### `status` — situation report, without modifying anything

Reports, without touching any file:
- Local files pending `feed`.
- Shared vault files pending `sync`.
- Points and vectors marked `not-detected-last-run`.
- Conflicts pending `resolve`.
- Virtual-to-real point merges pending or performed in the last
  run.
- HTML visualization: `allspark.html` nonexistent, up to date, or outdated
  (older than `allspark.md`) — it is only reported, never regenerated from
  `status`.

### `resolve` — decide a specific conflict

1. Shows the user, for a file or merge in conflict, both
   versions (the local one and the shared vault one) side by side.
2. Waits for an explicit user decision: which version prevails, or how to
   combine them.
3. Never picks "the most recent" or any other automatic criterion — the
   conflict is only closed with human confirmation.
4. When resolving, writes the agreed version both locally and in the shared
   vault, and removes the item from the `status` queue.

## Expected output

Each operation reports, without exception, how many files it touched and of
what type (repo MOC, repo point, virtual point, vector, merge), and makes
explicit any conflict left pending `resolve` —
it never silently closes an operation with unresolved conflicts.
